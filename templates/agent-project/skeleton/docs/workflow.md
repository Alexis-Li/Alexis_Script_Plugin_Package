# {{PROJECT_NAME}} 工作流程

本文档规定改动从提出到完成要满足什么，以及与用户怎么配合。它适用于
任何参与本项目的人或 Agent，不依赖某个特定的工具。环境和检查命令见
[AGENTS.md](../AGENTS.md)。所有 Git 和 `gh` 操作在本仓库内执行。

本文档规定的是**要达到的结果**。达到结果的具体办法由执行者按自己的工具
选择。

## 1. 实现与审核分开

- 写改动的一方不审核自己的改动，也不复验自己的修复。审核来自另一个会话、
  另一个工具或用户本人。
- 多方同时工作时，同一个 Issue 同一时间只由一方发布内容；分派工作时，把
  任务的 Issue 编号和需要遵守的文档一并交给对方。

## 2. 什么问用户，什么不问

用户是 3D 美术，不写代码。

**必须由用户决定：**

- 项目特有的约定及其取值。
- 需求的增减和改变（requirements.md 的任何条目）。
- 阶段验收。
- 第 8 节中需要用户同意的那一级架构变更。
- 界面的操作方式。
- 一切对外的事：仓库公开、许可证、发布版本、把含有生产内容的图片或
  文件发到仓库以外。
- 在用户机器上安装或升级软件、运行环境或工具链，以及现有环境无法支持
  开发或存在明确上限时怎么办（见 AGENTS.md 的环境一节）。在项目自己的
  目录内安装已声明的依赖不在此列。

向用户提问时：只问必须由用户决定的事；给出推荐选项；用美术术语和图示；
先把不依赖答案的工作做完。

## 3. 分支与改动的去向

### 3.1 `main` 和开发分支

- `main` 只存放稳定版本：验收通过后的里程碑版本和发布版本。`main` 的
  内容只通过合并开发分支进入：不直接向它提交，任务的 PR 也不指向它。
- 日常开发在**开发分支**上进行。有正在进行的开发分支时，一切改动都进入
  它：小改动直接提交到它，PR 以它为目标并从它开分支。
- 开发分支命名为 `dev/<主题>`，主题用简短的英文小写加连字符（例如
  `dev/stage-0`）。它通常承载一次大的开发，即一个总工单及其子工单的改动。
  开发过程中发现的缺陷和计划外的工作不属于这个总工单，但同样进入当前的
  开发分支。
- 开发分支从 `main` 建立，在这段开发完成（阶段验收通过或发布）时合并回
  `main`；一个开发分支跨越多次发布时，每次发布时合并。合并回 `main` 是
  单独的一步，需要用户同意。
- 只有在没有任何开发分支进行中时，下表中"直接提交"的小改动才提交到
  `main`。此时需要做其他改动的，先建立开发分支。
- 动手前先确认当前有没有进行中的开发分支、自己在哪个分支上，并检查本地
  已有的改动。

### 3.2 改动的大小决定流程

| 改动 | 流程 |
| --- | --- |
| 文字、错别字、链接、格式；以及不改变代码、测试、工具、CI、打包、版本和产品决定的文档、规则、模板和 `CHANGELOG.md` 小改动 | 直接提交到开发分支。不进 PR 分支，不需要单独的分支、PR 和审核报告；随开发分支进入 `main` |
| 其他一切改动，包括所有代码改动 | 分支、PR、独立审核后合并到开发分支（第 4 节） |

直接提交也要运行适用的检查，使用普通提交，不改写已共享的历史。拿不准
属于哪一类时，走 PR。

## 4. 走 PR 的改动

### 4.1 任务

- 一次大的开发通常有一个总工单和下辖的子工单。开发线路中的每个阶段是
  一个总工单，每个任务是它的一个子工单。总工单写明目的和完成的标准
  （阶段的验收标准），并列出子工单。
- 开发中发现的缺陷和计划外的工作各开独立的工单，不必挂在总工单之下；
  与某个总工单有关时互相链接即可。
- 工单写明：目的、范围、不做什么、可检查的完成标准、依赖、是否需要
  用户。缺陷工单写明现象、复现办法和影响。
- 完成标准编号为 `AC-01`，引用需求编号（如 `F-10`）和项目规则的编号，
  不复述；写明用最低能验证它的测试层级来证明。建议的实现办法与已定的
  要求分开写。
- 任务范围以 roadmap.md 为准。范围需要变化时，先改 Issue 和 roadmap.md。
- 工单正文是任务需求和验收的唯一依据；动手前读完工单的正文和全部评论。

### 4.2 先想清楚再动手

| 改动类型 | 动手前要弄清楚 | 记在哪里 |
| --- | --- | --- |
| 局部功能或修复，不改模块接口和状态归属 | 实际的调用路径、改动位置、受影响的行为、怎么验证 | 任务 Issue 里的一段简短说明，不另写文档 |
| 新模块、新命令、跨模块功能，或改变公开接口、数据对象、状态与资源的归属 | 它在 architecture.md 中的位置、复用哪些已有能力、各模块的职责、数据与状态怎么流动、失败时怎么恢复、兼容性和必须保持的行为；每条完成标准用最低的哪一层测试来证明，以及要新增什么驱动场景、测试夹具或钩子才能让 Agent 无人值守地跑 | 已有的 Issue 或设计记录；动手前对关键设计做一次审核 |
| 做法取决于一个没验证过的假设 | 决定做法的那个未决问题 | 先用最小实验验证，再继续建设 |

只能由人在宿主软件里目视检查的设计，要先改到测试能观察为止；确实做不到
的，验收中写明它是手工检查及原因。

要点清楚后直接开始，不等待批准。已有设计够用时引用它；只有新的长期决定
才写 ADR。

只做当前任务需要的东西。不为设想中的将来需求预先搭抽象层、留配置项或
建空模块；不为没有实际触发条件的情况写重试、兼容层和兜底分支或为之写
测试。能删除资产或损坏用户工程的可达路径，要有针对性的检查。

验证范围：

- 开始时简要写明要证明什么行为、最小的检查是什么。必须的检查照常运行；
  只为未覆盖的完成标准、实际出现的失败或有证据的回归风险增加检查。
- 检查全部通过、完成标准已覆盖、没有阻塞问题时就停。修复之后只重跑受它
  影响的部分。

### 4.3 分支、提交、交付

- 从开发分支 `dev/<主题>` 开分支：新功能、工具和文档用 `feature/<主题>`，
  修复用 `fix/<主题>`，主题用简短的英文小写加连字符。一个分支只做一件事，
  只含这个 PR 的改动。
- 提交说明用英文，说明做了什么和为什么。不改写已推送的历史，不强制推送。
- 串行工作可复用同一个工作目录；多方同时写代码时，各用独立的工作目录，
  事先分清各自负责的文件。
- PR 描述按仓库的 PR 模板填写：对应的 Issue（用 `Refs #编号`，不用会自动
  关闭 Issue 的关键词，因为 Issue 要在验收、集成和评论汇总之后才关闭）、
  覆盖的 AC 和 R 编号、目标分支、起止提交的完整 SHA、实际运行的检查及
  结果、已知缺口。
- 交付后状态为**待审核**，实现者到此为止。

### 4.4 审核

- 审核者阅读任务要求和完整的改动，检查：完成标准是否达到、是否符合
  AGENTS.md 中的架构规则、受影响的调用方、兼容性、失败路径、是否夹带无关
  改动、交付描述是否与代码和证据相符。
- 每轮审核在 PR 上只贴一条结论：审核的起止 SHA（含比较基线）、范围、结论、
  已运行的检查，以及每个阻塞问题的触发条件、影响、证据、最小复现和完成
  条件。实验的构造、数据表和推导过程不贴；需要长期保留的写进代码说明、
  测试或文档。
- 审核问题只有三类：没有达到完成标准、违反架构规则、有能复现的错误。
  每个问题都要有证据：一个失败的例子，或一项变差的指标。"换一种做法
  会更好"不是审核问题，不要求返工；想换做法按第 6.2 节另行提出。严重程度
  和是否阻塞是两个独立的判断。
- 没有独立审核的 PR 保持**待审核**，不合并。
- GitHub 不允许 PR 作者批准自己的 PR。审核从作者的账号发布时，以评论
  记录审核的基线、范围、结论和证据；它不是 GitHub 的批准事件，也不因为
  从该账号发出就算独立审核。

**审核基线与集成检查：**

- 审核通过针对明确的范围和完整的提交 SHA，包括比较基线。未提交的工作不是
  被审核的提交；要审核就需要一份可复现的差异，并附上相关的未跟踪文件。
- 审核之后又影响该范围的改动，需要增量审核和相关测试。复用旧证据前，先
  检查改动的路径和依赖；说明被审核的代码及其前提为什么仍然成立。目标
  分支的变化和冲突的解决也可能改变行为，即使任务的头提交没变。
- 目标分支的漂移和集成结果，与"头提交没变"的核对分开检查。squash 或
  rebase 会改变提交身份，在 Issue 的进展评论或状态评论中保留被审核的范围
  和集成后的 SHA。
- 区分三类依据：本次实际运行的检查、查阅的历史结果、对源码的推断。
  自测本身不构成验收。CI 之外的检查和宿主软件里的验证需要各自的证据。
- 范围内的审核可以通过，而整个 Issue 的验收仍然未完成。
- 修复后的问题由独立审核复验后才算解决。

**R 编号与分类：**

- 先读完 Issue 里已有的审核问题，再在整个 Issue 内按 `R-001` 的形式编号。
  编号在修复和复验中保持不变。
- 声称已修复的问题保持**已修复，待复验**，直到独立审核复验。
- 未解决的事项分为四类：**已确认缺陷**、**待验证风险**、**验收缺口**、
  **后续候选**。后续候选只有经约定的范围变更才会成为阻塞项。每项写明完成
  条件和下一步由谁来做。

### 4.5 合并和关闭

- 合并前必须有针对 PR 最新提交的已发布审核通过结论。用户同意合并不能代替
  审核。合并前复查 PR 头和目标分支，评估审核之后的变化并运行受影响的
  检查。合并时确认合并的就是审核过的那个提交
  （`gh pr merge --match-head-commit <SHA>`）。
- GitHub 仓库开启 **Automatically delete head branches**，它只删远端分支。
  合并后运行 `git fetch --prune origin`，然后在工作目录干净、分支已包含
  在目标分支时，删除该分支的本地工作目录和本地分支；有未提交改动或未合并
  内容的，保留并如实报告，不动别的会话正在用的工作目录。
- 在任务 Issue 的进展评论中记录合并后的开发分支 SHA，连同 PR、覆盖的 AC
  和待办的验收。不在 PR 上另贴合并后 SHA 的评论。
- 完成标准全部达到、没有未解决的阻塞问题、需要的目视验收已通过、交付
  已在开发分支上后，关闭 Issue。研究和原型类任务按它自己的交付物关闭。
  关闭时一并汇总评论（第 10.5 节），状态评论写明 `已关闭`、最终审核、集成
  SHA 和验收结果，不另发关闭评论。把开发分支合并回 `main` 与发布是单独
  的步骤。
- 提交、推送、创建 PR、合并、更新工单、关闭和删除评论，都以任务的授权为
  准。

## 5. 审核问题与修复

- 先通过代码路径、约定或复现确认问题属实，再改。
- 改之前查实际的调用方和相关状态、资源的归属者，在问题的根源处修，不在
  下游打补丁。修完复查原问题和受影响的既有行为；仍然有效的证据可以复用。
- 不得靠吞掉错误、删除断言、放宽阈值或改写完成标准来让检查通过。认为
  某个检查本身有错，需要独立的证据并明确更正。修复若改变了接口或状态
  归属，回到第 4.2 节的设计步骤。
- 同一类问题在第三轮审核仍然反复出现时，停止叠加补丁，诊断根源，缩小改动
  或重新设计。已确认的阻塞问题保持阻塞。
- 风格偏好、结构偏好和与本次改动无关的改进不要求返工，记为后续候选。
  没有指标能衡量的分歧，保留现有做法。

## 6. 实验任务与算法的更换

不同的执行者对同一个问题会有不同的做法。别的 Agent 的信心、习惯、偏好的
风格或自称的能力都不是更换现有做法的证据。审核对照约定的契约和可观察的
结果，不对照审核者自己会写的实现。

### 6.1 实验任务

roadmap.md 中标明按实验任务方式进行的任务，结果事先不确定。它们额外遵守：

- **先定评价标准。** 动手前在 Issue 中写下要改善的指标、固定的输入集、基线
  数值、达到多少算成功，以及投入的上限。
- **到上限就停。** 到上限仍未成功，记录结果和未解决的问题，停下来汇报，
  由用户决定是否继续。这个上限只适用于探索性工作，不是普通修复的重试次数
  限制。
- **不改评价标准。** 不得通过放宽阈值、更换输入集或修改指标定义来让实验
  成功。认为评价标准本身有错时，单独提出并说明依据，经独立审核后再改。
- **留下结论。** 采用的做法，以及被否定的做法和否定它的数据，在所属 Issue
  中保留；长期有效的架构决定写入 ADR，并在交接中指向它们，不让新会话
  重复做实验。

### 6.2 更换已有的做法

做法之间的取舍用数据决定，不用意见决定，也不靠各方让步。

- **单独提出。** 认为核心做法有更好的替代时，开一个独立的工单，按 6.1
  的方式进行，不在别的任务或审核中顺带修改。在现有做法之内的针对性修正
  仍是普通的缺陷修复。
- **同一标准下比较。** 新做法和现有做法在同一套固定的输入和环境上并排运行，
  比较与任务相关的正确性、性能和兼容性。
- **整体替换，或者不换。** 新做法明确更好就整个换掉，否则原样保留。不把
  两种做法各取一部分拼在一起，不为迁就各方的偏好留下多套实现或兜底
  路径。组合方案需要自己的技术依据和同一标准下的证据；折中不是证明。
- **已定的事要有新证据才重新讨论。** 想推翻 ADR 或已定决定，先读它的依据
  和被否定的方案，再拿出其中没有的东西：一个可复现的失败例子、一项变化了
  的约束，或实测的提升。只是看法不同不构成理由。
- 现有指标衡量不了某个确实存在的问题时，先补上规则和检查，再用它来比较。
- 使用现有的宿主工具链。增加或替换工具链需要有任务上的实际需求，并评估
  安装、部署和兼容成本；个人偏好不够。遵守现有的授权和依赖规则，不另设
  一刀切的禁令。

## 7. 目视验收

<!-- 待定制：本节面向美术工具，因为用户要用眼睛判断结果。项目没有需要用户目视检查的产出时，整节删除，并在 AGENTS.md、roadmap.md 和 requirements.md 中删去对目视验收和验收包的引用 -->

### 7.1 什么时候需要

roadmap.md 中标明需要用户的任务，以及每个阶段验收。用户直接要求看
某个结果时也适用。其他情况不打扰用户。已经被自动验收覆盖的工作，不因此
增加一道人工关口。

### 7.2 验收包

交给用户看的结果放在不入库的 `reviews/` 目录下，一次验收一个子目录。
它包含下面各项中适用的部分：

- 一份一页以内的中文说明：这次看什么、怎么打开、请用户回答的具体问题。
  不含代码术语。
- 能在用户的软件中直接打开的结果文件。
- 固定视角的对比图或截图，需要时附上手工做的对照版本。
<!-- 待定制：写明本项目验收包还应包含什么（例如 LoomlineRetopo：高模、带线框的低模、两者叠加的固定视角对比图，以及规范检查结果的中文摘要；MtoULiveLink：Maya 与 Unreal 并排的联动录屏或截图） -->

交付前执行者必须自己先看结果，有明显问题的先修。说明中的问题要具体
（例如"肘部这三圈环线的间距合适吗"）。如实说明已知的不足。验收用的内容
属于生产素材，只在本机保留，除非用户授权发布。

### 7.3 用户的评语

- 把用户的原话记入对应的 Issue。
- 评语是线索，不直接等于规则。先弄清它背后的原因，再按性质处理：
  - 违反了已有需求或规则的是缺陷：修复，并补上漏掉的检查。
  - 能用原理或行业通行做法解释的：新增或修正规则，写明依据，实现检查。
  - 解释不了、属于个人习惯的：做成可调的设置，或调整默认值并注明这是
    偏好，不写成通用规则。
  - requirements.md 中没有的功能：与用户确认后改需求和开发线路。
  - 属于非目标的：向用户说明。
- 执行者认为某条评语与原理或通行做法不一致时，如实说明理由，与用户
  讨论，不直接照办。
- 目标是让同一类问题以后被自动检查发现。

### 7.4 阶段验收

- 一个阶段的任务完成后，在阶段总 Issue 中逐条列出验收标准的达成情况和
  证据，并准备阶段验收包。
- 用户决定：继续、调整后重新验收、停止或改方向。决定记入阶段总 Issue。
- 验收未通过时不开始下一阶段的任务，标明可并行的任务除外。处理办法见
  roadmap.md 末尾。

## 8. 架构变更

architecture.md 是开发的边界。改动它分两级。

**需要用户同意的：**

- 违反或修改任何一条架构决定（AD 编号的条目）。
- 改变模块的依赖方向或职责边界，让某个部分承担本应属于别处的逻辑。
- 任何会改变用户看到的东西或操作方式的结构调整。

处理办法：停下，不先实现再补手续，也不用绕路的办法规避；说明遇到了什么
问题、为什么现有架构解决不了、建议怎么改、还有什么别的办法；用用户
能懂的话说明这对他意味着什么、风险和代价，取得同意；写一份 ADR 并在同一
次改动中把 architecture.md 改写为新的现状；然后才改代码。

**不需要用户同意的结构细节：** 模块和目录的名字与划分、数据对象的字段、
命令的清单和参数、测试的组织方式。这些随开发调整是正常的：在同一次改动中
更新 architecture.md，影响面大的写一份 ADR，按普通改动审核。

architecture.md 没有写到的事属于普通的实现选择，由执行者决定，不需要
任何手续。其中"留待以后决定的事"由指定的任务决定并写 ADR。

ADR 的写法见 [adr/README.md](adr/README.md)。

## 9. 样本

- 用户的生产素材只放在不入库的 `samples/` 下，每套一个子目录，目录名
  用中性的代号（如 `set-a`），不用项目或角色的真实名称。
- 每套样本附一份说明：包含哪些文件、各自的角色，以及用户提供的备注。
<!-- 待定制：写明本项目一套样本包含什么（例如 LoomlineRetopo：减面高模、手工低模和用户的手工用时；MtoULiveLink：一份真实的 Maya 场景和对应的 Unreal 资产与序列；StoUTextureSync：一个 Painter 项目及其导出设置） -->
- 在 Issue、PR、提交说明和入库的文档中只用代号提到样本。
- 含有生产内容的图片和文件只放在 `reviews/` 中。未经用户同意，不上传到
  Issue、PR 或任何外部服务。程序生成的标准数据不含生产内容，它们的图片和
  文件可以发布，用作审核的证据。
- 自动测试不读取 `samples/`。

## 10. 文档、Issue 和评论

### 10.1 当前状态与信息归属

- 文档、Issue 和评论都写成当前的事实。决定过时了，取得同意后在原处改写，
  不保留"之前……现在……"的叙述；新决定取代它之前，旧决定继续有效。
- 每类内容只有一个存放处，别处只引用。Issue 和 PR 里讨论出的新结论或对旧
  结论的修改，在同一次改动中写回对应的文档，Issue 里只留一句指向（如
  "已写入 F-12"）。
- 改动让某份文档的说法不再成立时，在同一次改动中改写那份文档；审核时
  把它当作改动的一部分来查。

| 内容 | 存放处 |
| --- | --- |
| 词语的确切含义 | CONTEXT.md |
| 需求、非目标、质量要求 | docs/requirements.md |
| 结构、模块职责、架构决定 | docs/architecture.md |
| 长期决定及其依据 | docs/adr/ |
| 阶段、任务的范围与完成标准 | docs/roadmap.md |
| 用户手册：兼容性、安装、使用、限制 | README.md、README_CN.md |
| 版本变化 | CHANGELOG.md |
| 任务的要点和验收标准 | 任务 Issue 正文 |
| 改动范围、交付、审核问题和检查结果 | PR 描述与审核评论 |
| 新的进展、审核和验收事实，集成结果 | Issue 的普通评论 |
| 整理或关闭时的当前状态 | Issue 的状态评论 |

<!-- 待定制：本项目若有其他长期存放的内容，在此增行并写明唯一的存放处（例如 LoomlineRetopo：topology-rules.md 存放合格标准；MtoULiveLink：protocol/README.md 存放跨宿主协议，docs/history/ 保留选定的历史证据） -->

### 10.2 评论

- 进展、审核和验收各用普通评论。自己的评论有错或过时，在原处改写；新评论
  只写新事实。
- 每条新评论以一到三行的 `**当前状态**：…` 结尾，说明整个 Issue
  现在的状态（不只是这条评论的话题）、下一步和由谁来做，使最新一条评论
  就是当前状态。两次整理之间不为了保持最新而去改旧的状态评论。
- 评论要短，过时的删除。接手的人和工具读工单时会把全部评论读进去（网页上
  折叠的评论也一样），留着的每一条都应当仍然成立。
  - 新的进展、审核或状态评论保存之后，删除被它完全取代的旧评论：旧的进展
    说明，或者新审核已按编号列出其全部问题及结果的上一轮审核。
  - 写明做法要点、决定或仍被依赖的证据的评论保留，并随内容的变化在原处
    改写。
  - 删除之前，确认以后需要的内容已经在更新的评论、文档、ADR、测试或接手
    它的工单里，并替换指向将被删除评论的链接。删除时按精确的评论 ID 进行
    （见 10.4）。
  - PR 合并时保留它的描述、合并头提交的最终审核和仍然有效的评论。
- 把整个 Issue 汇总成一条状态评论，只在用户要求整理或 Issue 关闭时进行。
- 发布的内容中不出现本机路径、用户目录、密钥和样本的真实名称，用
  `<scratch>`、`<samples>/set-a` 这样的占位写法。

### 10.3 状态评论

用户要求整理或关闭 Issue 时，产出一条状态评论。用 `tools/issue_report.py`
的 `template` 和 `check` 子命令生成和校验；它的状态和下一步小节兼作评论
的结尾。普通的进展、审核和验收评论写各自适用的内容，加上 `当前状态`
结尾。PR 描述用仓库的 PR 模板。

```markdown
<!-- issue-status:v1 issue=65 -->
## 状态

- 状态：进行中 / 待审核 / 待验证 / 受阻 / 可关闭 / 已关闭
- 基线：完整实现、最终审核和集成 SHA 或包版本，说明尚未完成的阶段
- 更新日期：YYYY-MM-DD

### 简介
### 相关提交
### 已完成
### 未完成
### 开发边界
### 决定
### 宿主验收
### 下一步
```

- **简介**：Issue 的目的和当前结论。
- **相关提交**：PR 和提交的完整 SHA 及简短用途，最终审核的链接。基线要区分
  实现、审核和集成。
- **已完成 / 未完成**：按 AC 或需求编号给出结果、证据链接、未解决的审核
  问题、验收缺口和完成条件。`可关闭` 或 `已关闭` 要求全部约定的验收已覆盖
  且没有阻塞问题。
- **开发边界**：包含什么、不包含什么、移到别处的事项、证据的局限。
- **决定**：现行的决定，链接到维护它的 ADR 或需求。
- **宿主验收**：被测的 SHA 或包、确切的宿主版本和相关环境、中性的样本代号、
  复现步骤、带单位的测量值、每条 AC 的结果、未测的场景。区分本次运行的
  检查和历史证据，复用旧证据要说明理由。不适用时写 `无`。
- **下一步**：具体的下一步行动和负责人；已完成时写 `无`。

首行标记和小节顺序保持不变；每个小节都要填，没有内容时写 `无`。日期按
任务所在的时区。检查脚本校验结构、状态、日期和可移植的路径；证据是否属实、
链接是否可用、有没有未解决的阻塞问题、前后是否自洽，由发布者核对。

### 10.4 安全发布

草稿放在 AGENTS.md 规定的临时目录里生成：

```powershell
python tools/issue_report.py template --issue <n> --output "<scratch>/issue-<n>-status.md"
python tools/issue_report.py check "<scratch>/issue-<n>-status.md" --json
```

发布前替换掉所有占位内容。模板命令不覆盖已有文件。退出码：0 成功，1 内容
或文件有误，2 命令用法有误。

- 写之前先读 Issue 并翻完全部评论。状态评论按标记和 Issue 编号匹配；匹配到
  多条时，先弄清楚，再按精确的评论 ID 编辑。共用账号时绝不用
  `--edit-last`。
- 新建评论：`gh issue comment <n> --body-file <草稿>`。
- 编辑前先读 `gh api repos/{owner}/{repo}/issues/comments/<id>`，核对
  `issue_url`、作者、正文、标记和 `updated_at`；写入前立刻再读一次，处理
  期间发生的改动。完整正文放进一个 UTF-8 的 JSON 文件，用
  `gh api --method PATCH repos/{owner}/{repo}/issues/comments/<id>
  --input <payload.json>` 提交。写完读回保存的正文并返回链接。遇到含糊的
  超时，先读再重试。
- 同一个 Issue 的写入串行进行；分派出去的工作由一个协调者统一发布。先读后
  写不是原子锁。
- 多行的 Issue、PR 正文和评论一律用 `--body-file`。

### 10.5 关闭与整理

只在用户要求整理或关闭 Issue 时汇总评论，除非另有限定，下面各步都做：

1. **清点。** 读 Issue、全部评论、链接的证据、两处临时目录和任务产出的文件。
   弄清归属和是否仍在使用；共用的输入和拿不准的文件保留。
2. **保留有用的知识。** 以后做决定或做回归检查还需要的内容，移到维护它的
   文档里（ADR、README 或其他相关文档）；需求留在它所属的 Issue 或文档。
   扩充已有的存放处，并在状态评论中链接它；过时的内容丢弃。删除来源评论
   之前，先在授权范围内提交并发布必要的仓库内容；无法发布时，保留依赖它的
   评论并报告未完成的事项。
3. **汇总。** 创建或编辑经过校验的状态评论：当前结论、有用的证据和下一步。
   关闭时写 `已关闭`，包含最终审核、集成 SHA 和验收结果。读回保存的评论并
   核对链接；把指向将被删除评论的引用换成它们的存放处。
4. **清理。** 重读要删除的评论，处理期间的并发改动，再按精确 ID 删除其余
   评论。需要的证据已进入它的存放处后，清除任务自己的临时文件，包括辅助
   脚本、草稿、请求体和结果；删除前核对解析后的路径，共用的和拿不准的文件
   保留。
5. **核对。** 翻完全部评论，确认只剩一条状态评论；在最后一次辅助脚本运行
   之后，检查证据链接、发布状态和临时文件。清理不完整的，报告原因和下一步。
   验收和集成都完成时，不另发关闭评论就关闭。

关闭 Issue 与发布产品是两件独立的事。

## 11. 版本、变更记录与发布

- 第一个交到用户手上的版本发布时建立版本号，从 0.1.0 开始。何时定为 1.0.0
  由用户决定。
- 只有发布改动修改版本号，其他 PR 不动它。
- 有用户可见变化的改动在 `CHANGELOG.md` 的 `## Unreleased` 下加一条，用
  用户的话写，每条一两行并以 `(#编号)` 结尾；发布改动把这个标题改成版本号
  和日期。分组和写法见 AGENTS.md 的版本与变更记录一节。需要用户做什么的
  变化（重装、重设、替换被移除的功能）写进 `### Upgrade notes`。
<!-- 待定制：写明版本号所在位置，以及改版本和打包的命令，包含的各部分是否使用同一个版本号（例如 MtoULiveLink：Maya 与 Unreal 两个组件同版本，用 tools/version.py 改版本、tools/package.py 打包到 releases/；LoomlineRetopo：算法核心和各插件同一个版本号） -->
- 发布标签为 `v<version>`。发布前，从打包出的压缩包验证安装，再发布。
- 本仓库作为子模块挂进集合仓库时，集合只把 pin 更新到已发布且审核过的提交，
  不跟随开发分支的最新提交。
