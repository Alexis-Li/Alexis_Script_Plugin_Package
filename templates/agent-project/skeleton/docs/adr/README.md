# 架构决定记录（ADR）

ADR 记录新的**长期决定**及其依据，让后来者不必重新讨论，也不重走被否定的
弯路。普通的实现选择不写 ADR。

## 什么时候写

- 做出了影响多个模块、会长期保持的决定：技术路线、依赖的取舍、数据格式、
  跨模块的契约。
- 按 [workflow.md](../workflow.md) 第 8 节取得用户同意的架构变更：先写 ADR，
  并在同一次改动中把 [architecture.md](../architecture.md) 改写为新的现状。
- 实验任务结束时（workflow.md 第 6.1 节）：采用的做法、被否定的做法和
  否定它的数据。

## 怎么写

- 文件名 `NNNN-简短英文标题.md`，编号四位、依次递增，标题用小写加连字符
  （例如 `0003-use-json-for-documents.md`）。
- 用中文写，章节依次是：背景、决定、依据、后果、考虑过的其他做法。
- 写成当前状态，不写讨论经过。被后来的 ADR 取代的决定，在原文的决定一节
  用一句话指向取代它的 ADR，并说明取代了哪一部分。
- 已定的决定要有新证据才重新讨论：一个可复现的失败例子、一项变化了的约束，
  或实测的提升。重开之前先读它的依据和考虑过的其他做法。
- 决定生效后，architecture.md 中受它影响的部分在同一次改动中改写，并指向
  这篇 ADR。

## 模板

复制下面的内容建立新的 ADR：

```markdown
# NNNN 一句话写出决定

## 背景

要解决什么问题，现有的约束是什么。

## 决定

做什么，不做什么。

## 依据

支持这个决定的证据：测量的数据（写明环境和输入规模）、原理、已有的约束。

## 后果

这个决定带来的约束和需要跟进的事；哪些文档或模块因此改变。

## 考虑过的其他做法

- **做法 A。** 为什么没有采用。
- **做法 B。** 为什么没有采用。
```
