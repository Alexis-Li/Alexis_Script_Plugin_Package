## 1. 项目目的、用户痛点和成功标准

### 1.1 为什么要做

日常流程是：SP 绘制 / 调参 → 手动导出 → UE 导入 / 重导入 → 查看材质 → 返回 SP 修改。问题不是缺少一个新的材质球，而是**重复操作阻断制作节奏**。SP 自身预览也不等同于 UE 正式场景渲染，最终判断仍应在 UE 完成。

### 1.2 想达到什么效果

首次绑定后，在 SP 中照常绘制或调整材质；操作告一段落后自动输出需要更新的贴图；UE 将更新应用到**已经存在**的 Texture 资产，原有材质引用保持不变；美术人员直接在 UE 原生视口查看最终效果。

```text
SP 正常绘制 / 图层参数改变
  → 有效纹理变化事件
  → 防抖、去重、串行任务调度
  → 按预设导出到暂存目录并验证
  → 以安全方式发布到约定源贴图路径
  → UE 重新导入已有 Texture 资产（首选 Auto Reimport）
  → 原材质 / 材质实例引用不变
  → UE 原生视口显示新效果
```

### 1.3 成功标准

1. **无重复操作**：完成首次配置后，常规绘制无需手工导出或手工重导入。
2. **准确**：只更新绑定的贴图，通道与文件不混淆，不破坏正式材质。
3. **稳定**：最终状态能追上 SP 最新版本，错误可诊断、可恢复。
4. **资源可控**：在 32GB 机器上不因插件造成持续排队、缓存膨胀、重复导入或不可接受的卡顿。
5. **效果可见**：直接用 UE 视口判断材质，不需要任何 UE→SP 渲染回传。

> “自动热更新”指绘制停止后自动触发的**近实时文件同步**，不承诺画笔运动期间逐帧更新，也不承诺零延迟。

### 1.4 用户侧操作流程

**首次配置（一次性）**

1. 在 UE 中确认目标角色部件已使用项目原有的 Master Material / Material Instance，各贴图参数引用的是既有 Texture 资产。
2. 确认这些 Texture 的源图片路径及项目打包规则（如 `BaseColor / Normal / ORM`）。尚未建立资产时，先按正常资产流程导入并连接材质；插件不生成或修改材质球。
3. 按 **D1（§3）** 的结论准备源文件位置：同步写入的目录必须与正式源贴图的存放与提交规则相容。在 UE 中配置限定范围的 Auto Reimport。
4. 在 SP 中打开对应工程，选择要同步的 Texture Set、导出预设、文件路径和目标映射，执行一次手动同步校验。
5. 核对 UE 原有 Texture 是否刷新，检查通道、sRGB、法线方向及材质表现。校验通过后启用自动同步。

**日常制作（目标体验）**

在 SP 中绘制或调整图层 → 停止操作并经过可配置的空闲时间 → 插件合并变化、导出并安全更新源文件 → UE 重导入已有 Texture → 直接查看 UE 视口。资源紧张时可一键切换到低分辨率或仅手动同步。

**项目收尾（正式发布）**

通过明确的“正式发布 / 完整分辨率导出”操作，按项目要求的精度和通道配置输出正式贴图；只有用户确认后才覆盖正式资产所需的源文件。预览图与正式贴图不能仅凭文件名区分。

| **P1 / 生产可用** | 基础原型通过后、长期使用前补齐 |

- 不接管、重建或强制改造 UE Master Material / Material Instance。

- 不为传图创建常驻渲染器、GPU 图像回读系统或 SP 预览窗口。
- 首版不要求 UE Editor 插件；先验证 UE 自带 Auto Reimport。
- 正式发布与临时预览有明确边界，低分辨率预览不能无提示地进入正式资产（见 D1）。

## 3. M0 必须给出结论的关键决策

以下决策影响数据模型、配置结构和产品形态，必须在 M0 结束前定案并记录到总 Issue，不能留到开发中途。

### D1：预览贴图与正式贴图如何共存【最高优先级】

FR-04 要求更新“已有 Texture 资产”，FR-05 默认导出 2K 预览，且“不能移改材质引用”排除了“另建一套预览 Texture 并切换材质参数”的做法。如果预览与正式写入同一个 Texture 资产，2K 预览一旦重导入，`.uasset` 内容及其关联源文件都会变为预览版本。可选方案：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **(a) 预览即正式分辨率** | 预览与正式使用相同分辨率和通道配置，只靠空闲触发和防抖控制频率；“正式发布”只负责确认与提交 | 单次导出与重导入成本更高，需 PoC-04 证明可接受 |
| **(b) 预览降分辨率 + 不保存约定** | 允许 1K/2K 预览写入同一资产；预览期间被标脏的资产不保存，正式发布时以完整分辨率重新导出并重导入 | 依赖用户纪律或额外保护；需验证源代码管理与自动保存下的风险 |

M0 需要用实测数据（PoC-01、PoC-04）在 (a)/(b) 中选择，或证明另有不违反约束的方案。在 D1 定案前，首次配置第 3 步的源文件目录方案也不能定稿。

### D2：产品形态与实现路线

- **路线 A（首选）**：SP 插件 + UE 原生 Auto Reimport，无 UE 侧代码。产品为单一 SP 组件，放在 `substance-painter/plugins/SPtoUTextureSync/`，UE 端配置写在 README 中。
- **路线 B（触发式升级）**：SP 插件 + 极简 UE Editor 模块，构成跨宿主产品 `composite/SPtoUTextureSync/`（含 `substance-painter/` 与 `unreal/` 两个组件）。
- 升级条件见 §6.2；决策依据为 PoC-01、PoC-04、PoC-05、PoC-06 的实测结果。

### D3：版本基线

- **UE**：沿用仓库已有基线，即官方原版 Unreal Editor 5.7.4 与 Topia Engine 5.7.4。
- **SP**：确认实际使用的 Painter 版本。版本决定内置 Python 与 Qt 绑定（PySide2 / PySide6）的选择，以及 `substance_painter` API 的可用行为。

### D4：短暂“部分贴图已更新”是否可接受

纯文件方案下，UE 无法保证 BaseColor / Normal / ORM 同时切换。M0 需由用户在实际资产上确认这种短暂不一致能否接受；不能接受时，这本身就是路线 B 的触发条件。

## 4. 功能需求

### FR-01：SP 纹理变更监听与自动导出【P0 / R】

**需求**：绘制、图层参数调整、材质参数变化等最终改变纹理内容的操作，能够自动发起同步。

**验收要求**：

1. 监听官方 `TextureStateEvent`，利用其提供的 Texture Set / Stack、通道、UDIM Tile 等标识；事件回调只记录状态并排程，不直接执行导出或磁盘 I/O。
2. 按 **Texture Set** 导出（必要时进一步限定 Stack、输出贴图及 UV Tile），不默认全工程导出。
3. 连续变化合并为一次任务；尚未执行的过时任务可被替换；已开始的导出不假设能被安全中断。
4. 同步可开启、暂停和恢复，支持“立即同步”和“重新完整同步”。
5. 只显示**可确认的真实状态**，如“等待修改结束 / 导出中 / 已发布到源文件 / 失败”。
6. 导出期间若检测到新修改，该轮完成后再次检查是否需要输出新版本。
7. 通过工程生命周期事件（工程关闭、切换、退出编辑等）作废失效任务；Texture Set 关闭或预设变化也会使任务失效。
8. 利用 SP 的忙碌状态事件（如 `BusyStatusChanged`）避开 SP 正在进行烘焙、计算等繁重操作时发起导出；具体事件以目标版本 API 为准。

**允许妥协**：不支持逐笔 GPU 增量或绘制过程中的 60FPS 更新；允许绘制空闲后延迟同步。某些不触发纹理事件的修改可以由手动同步兜底，覆盖范围以 PoC-02 实测为准。

**技术依据**：`substance_painter.event.TextureStateEvent` 报告纹理新增、移除或更新；官方事件节流参数最低为 500ms，**这不等于整条同步链路能在 500ms 内完成**。

### FR-02：JSON 导出预设与通道映射【P0】

**需求**：输出格式与颜色通道不写死在程序中，而是由可维护、可保存的配置驱动。

**每个同步配置至少包含**：

- SP 工程标识、Texture Set / Stack 标识、输出目录。
- 每张输出贴图的文件名、通道来源、目标通道和打包顺序。
- 格式、位深、分辨率、法线方向、是否启用。
- UDIM 标记及 Tile 范围（如项目使用）。
- UE 目标源文件路径或期望的 Texture 资产路径（仅用于映射校验，不更改材质）。
- 预览与正式发布两套输出配置（具体关系按 D1 结论确定）。

**示例映射（必须可自定义）**：

| 输出贴图 | 通道内容 | 说明 |
| --- | --- | --- |
| BaseColor | RGB = Base Color | sRGB 颜色数据 |
| Normal | RGB = Normal（按项目约定的法线方向） | 通常使用法线压缩设置 |
| ORM | R = AO，G = Roughness，B = Metallic | 常见 UE 打包方案之一 |
| AoMetalRough | R = AO，G = Metallic，B = Roughness | **与 ORM 顺序不同，不能视为同一布局** |
| Emissive / Opacity / Height | 单独启用，按项目设定 | 可选扩展 |

**硬性边界**：默认预设必须明确标注每个通道的含义；首次启用时提供预览检查或测试色块验证。配置文件由本项目独立编写。

### FR-03：导出预检查、发布与一致性【P0】

**需求**：UE 只能看到已完成且通过验证的贴图，不读取半成品，不误覆盖其他文件。

1. 导出前通过 `list_project_textures()` 获取预计输出清单，检查文件名冲突、路径越界、重复映射与缺失配置。
2. 在**不受 UE 监控的暂存目录**完成导出，检查 API 返回状态、文件是否存在、大小非零、期望输出是否齐全。
3. 整批满足发布条件后，才把文件发布到 UE 监控目录。
4. 发布采用同卷“临时文件 → 完整写入 → 原子替换单个目标文件”。Windows 上目标文件可能被 UE 或其他程序占用而替换失败，必须有限次重试，失败时上报并保留旧文件。**多个文件之间不存在跨文件原子事务。**
5. UE 目录监听可能把一次替换识别为“删除 + 新建”或“修改”。必须在 PoC-01 中确认这种行为不会因关闭 Auto Create / Delete Assets 而导致资产被跳过或误删。
6. 每次发布记录批次版本、文件列表及哈希 / 尺寸；版本信息写在插件自有的清单文件中，不改变 UE 可见的文件名。
7. 失败时保留上一批可用文件，日志指出失败阶段，并允许重新完整同步。
8. 禁止自动删除用户的正式源贴图；缓存清理只作用于插件创建并可识别的临时文件。

### FR-04：UE 既有 Texture 资产重导入【P0 / R】

**需求**：SP 侧只更新约定的源图片，UE 将变更重新导入已引用这些图片的 Texture 资产，插件不控制材质节点。

**首选：UE 原生 Auto Reimport**

1. 用户首次将源图片导入 UE，并用现有材质或材质实例引用该 Texture。
2. 确认 Texture 记录的源文件与 SP 发布路径一一对应。
3. 在 Editor Preferences → Loading & Saving → Auto Reimport 中设置监控目录，只监控目标源文件目录和必要的扩展名。
4. **关闭监控目录的 Auto Create Assets 与 Auto Delete Assets**；源代码管理环境下是否启用“重启后检测变更”单独决策。
5. 联合验证 Import Threshold Time 与 SP 空闲时间（§6.4）。
6. 验证 UE 在后台时的行为：用户绘制时 SP 在前台、UE 在后台。编辑器的“后台时降低 CPU 占用”（Use Less CPU when in Background）等设置可能延迟甚至暂停重导入。必须实测并在配置指南中给出建议设置。

**强制保护**：

- 不重建 Master Material，不调用清空材质节点之类的操作。
- 不清空 Material Instance 的参数覆盖或材质基础属性。
- 不创建新材质球，不更改原有贴图引用。
- 不覆盖映射不明确、路径不匹配或属于其他项目的 Texture 资产。
- 保留 Texture 既有的 sRGB、Compression Settings、Virtual Texture 等导入配置；检测到不合理配置时提示，不直接修改。

**状态边界**：仅使用 Auto Reimport 时，SP **最多能证明文件已安全发布**，不能声称“UE 已导入成功”。要获得后者，需要 UE 侧可验证的回执（路线 B）。

**数据模型**：SP 输出的是磁盘图片（PNG / TGA 等），材质实例引用的是 UE Texture 资产（`.uasset`）。自动化链路是“源图片变更 → 已有 Texture 资产重导入”，不是让材质绕过 Texture 资产直接读取图片。

### FR-05：32GB 机器的资源压力控制【P0 / R】

插件无法降低 SP 与 UE 本身的内存占用，只能控制它新增的峰值、排队与 I/O。降低导出分辨率也不会降低 SP 内部的图层计算压力；同一 Texture 在 2K 与 4K 之间切换还可能增加重导入成本。

**P0 要求**：

1. 默认同一时间只运行一个导出批次，并限制待处理批次数量。
2. 高频修改时防抖、去重，每个目标只保留最新的待同步版本。
3. 默认空闲触发 **3 秒**，可调整（原型测试范围 1–10 秒）。
4. 预览分辨率档位与默认值按 D1 结论确定；始终提供手动完整分辨率导出。
5. 自动同步 / 仅手动同步一键切换；连续出错或严重卡顿时能及时停用。
6. 不常驻保留大尺寸解码贴图副本；临时文件有清理策略和明确的大小上限。
7. 用足够保守的导出间隔和 UE 监控阈值，避免 SP 生成下一批时 UE 仍在反复处理上一批，造成任务堆积。纯文件方案下 UE 的导入节奏不能完全由 SP 控制。
8. **单次同步造成的 SP 停顿有上限**：`export_project_textures` 很可能是阻塞调用，导出期间 SP 界面会短暂停顿。M1 前必须测出停顿时长（PoC-02），并定出可接受的上限；超过上限时自动降级（减少输出、降分辨率或切换手动）。同步失败不能使工程处于无法继续绘制的状态。

**P1 增强**：采集 Windows 可用内存、提交量、SP/UE 进程占用、GPU 专用与共享显存以及导入耗时，按压力推迟、降分辨率或切换手动模式。阈值必须来自实际工作机测量，自动决策允许用户覆盖。系统已严重分页时，优先停止自动同步，而不是持续重试。

### FR-06：多 Texture Set 与配置持久化【P1】

- 按工程保存多个 Texture Set 的启用状态、输出路径、导出预设和目标映射。
- 支持多个独立角色部件（头、身体、外套、鞋等）；首版不要求自动识别 UE 组件。
- 允许单个 Texture Set 暂停同步。
- 重启 SP 后恢复上次有效设置，不同工程之间的配置不能串用。可以存入 SP 工程 Metadata 中插件专属的键，但不能把磁盘路径当作永久唯一标识。
- 工程路径或 Texture Set 变更导致映射失效时，必须要求用户重新确认。
- 首版接受手动绑定，以后再考虑自动发现与绑定向导。

### FR-07：状态、日志与异常恢复【基础故障提示 P0；其余 P1】

**状态**：待同步、导出中、导出已完成、已发布到监控目录、等待 UE 确认（可能无法观测）、UE 确认完成（仅在有实际回执时）、失败、已暂停。

**异常场景**：UE 未启动、SP 意外关闭、磁盘满或无权限、输出路径不存在、源资产被移动、Texture Set 重命名、导出 Warning / Error、Auto Reimport 未生效、目标文件被占用、源代码管理冲突。

**恢复规则**：

- 没有当前阶段确实完成的证据，就不声称同步成功。
- 中断时保留最后一次成功发布的文件；重新开始后可执行一次完整导出。
- 任务使用单调递增的版本号，旧结果不能覆盖新版本。
- 日志包含 Texture Set、导出预设、目标文件、版本、耗时和失败原因。
- 优先依靠“手动重新完整同步”恢复，不做复杂的多级重试队列。

### FR-08：SP 停靠面板【最简面板 P0；完整面板 P1】

**P0 最简面板**（M1 必需，日常操作不依赖控制台）：

- 当前工程与 Texture Set、自动同步开关、“立即同步”“完整同步”“暂停”。
- 最近一次结果（成功 / 失败及耗时）；没有 UE 回执时明确显示“文件已发布，UE 状态未知”。

**P1 完整面板**：导出预设与输出目录选择、空闲等待与预览分辨率、映射检查、缓存清理、打开日志。

UE 侧不开发第二套 UI；首次设置 Auto Reimport 依靠配置指南引导。

### FR-09：UE→SP HDR 光照环境【P2 / R】

独立实验：在 UE 中选中模型的位置捕获 HDR 环境，导入 SP 做**近似**灯光预览。只要求整体照明趋势接近，不还原 Lumen、阴影、反射或后处理；手动触发，不占用持续渲染资源。收益小或维护成本高时可以永久不做。

### FR-10：摄像机同步 / 贴图自动绑定【P2】

一键对齐视角、自动识别材质槽、批量配置源贴图等，在核心同步稳定后再决定，不作为首版依赖。

## 6. 架构与实现约束

### 6.1 路线 A：SP 插件 + UE Auto Reimport【首选】

**SP 侧**：Python 插件监听纹理事件、合并更新、按配置导出，使用本机暂存目录与固定发布路径；UI 使用 Painter 内置的 Qt 绑定。

**UE 侧**：不安装额外插件；用源文件预先创建 Texture 资产并连接到现有材质；开启 Auto Reimport，对选定目录中的既有源文件重新导入。

优点：组件最少，维护成本低，没有常驻通信进程，不需要二次渲染。限制：UE 的重导入节奏和成功回执不受 SP 控制；资产处理仍会占用 RAM、VRAM、CPU 和磁盘 I/O。

### 6.2 路线 B：SP 插件 + 极简 UE Editor 模块【触发式升级】

已尝试降低同步频率等低成本措施后，PoC 仍发现以下任一问题时才启用：

- Auto Reimport 高频重导入造成不可接受的卡顿或资源峰值。
- 需要更可靠的批次调度与最终一致性检查（D4 不可接受）。
- 用户必须知道 UE 某次重导入的真实成功或失败。
- Auto Reimport 对源路径、监控目录、后台状态或特定 Texture 的更新行为不可靠。

UE 模块只负责：接收完成通知、定位白名单内的 Texture 资产、串行重导入、校验并回执。**不创建材质球，不改材质节点，不传输渲染图像。** 通信可用本地 HTTP / WebSocket 或可靠的文件消息，贴图本身仍走磁盘路径。是否需要常驻服务由实测决定。该模块独立实现，遵守 `unreal/AGENTS.md`。

### 6.3 仓库位置与代码分层

- **路线 A**：`substance-painter/plugins/SPtoUTextureSync/`，独立 SP 插件，自带 README 中英双版、CHANGELOG 和 LICENSE；UE 配置指南写在 README 中。
- **路线 B**：`composite/SPtoUTextureSync/`，下含 `substance-painter/SPtoUTextureSync/` 与 `unreal/SPtoUTextureSync/`，产品元数据放在 composite 根目录。
- 进入开发时，本提案的内容按 `docs/proposals/README.md` 迁移后删除。
- **分层**：调度器、配置解析与校验、暂存 / 发布、版本号与清单等逻辑放在不导入 `substance_painter` 的纯 Python 模块中，在 SP 之外用单元测试覆盖，仓库 CI 可以运行；事件连接、导出调用与 UI 放在很薄的 SP 适配层，只在 SP 中验证。
- 仓库的打包、版本更新与项目模板命令目前不覆盖 SP（见 `substance-painter/AGENTS.md`），由 REPO-01 补齐。

### 6.4 关键技术约束

- SP 空闲等待、文件监听和 UE Import Threshold Time 各自带延迟，叠加过多会让同步迟钝；三者必须**联合测试**，不是越大越稳。
- 不在监控目录中直接写入未完成的导出文件。
- 预览与正式分辨率的关系按 D1 处理；改变正式 Texture 分辨率时，需评估源文件变化、资产标脏、流送池变化和保存风险。
- UDIM / Virtual Texture 需要专门验证导出命名、Tile 顺序与 UE 导入机制，不能因为普通二维贴图通过就宣布支持。
- `close_plugin()` 必须断开全部事件连接、移除 UI、停止计时器与线程；重复加载不能产生重复的处理器。

## 7. PoC（技术验证）与测量要求

先验证，再决定编码范围。所有性能指标以 **32GB 实际电脑及接近真实角色项目的规模**为准。PoC 编号与 §9 的 Issue 编号一一对应。

### PoC-01：最小文件同步闭环与 Auto Reimport 行为【最优先】

1. 选一套 SP 服装 Texture Set，用固定命名输出 BaseColor、Normal 和项目实际使用的打包图。
2. 在 UE 中建立原有材质引用与源文件映射，关闭 Auto Create / Delete Assets，设置有限的监控目录。
3. 手动替换一次源文件（含“原子替换”方式），确认 UE 原有 Texture 按预期刷新，并记录目录监听看到的事件类型。
4. **UE 置于后台**（SP 在前台）时重复第 3 步，分别测试“后台时降低 CPU 占用”开启与关闭，记录刷新是否发生及延迟。
5. 再实现 SP 侧最小自动导出，确认“绘制结束后自动更新 UE”的完整闭环。
6. 人为让其中一张图导出失败，检查 UE 是否读取半成品，以及错误反馈。
7. 记录 Texture 是否被标脏、保存时是否产生源代码管理噪声（为 D1 提供依据）。

**通过条件**：没有手动重导入，没有错误覆盖资产，材质球未被修改，失败可判断；后台行为已记录并给出推荐设置。

### PoC-02：SP 事件覆盖、空闲调度与导出停顿

1. 记录笔刷绘制、图层参数、材质参数、填充层、遮罩、烘焙等操作是否触发 `TextureStateEvent`，以及事件携带的标识。
2. 验证防抖、去重和“导出期间又有修改”的重排程逻辑。
3. 测量单次导出期间 SP 界面停顿的时长（中位数与 P95）及其与分辨率、输出数量的关系，为 FR-05.8 的上限提供数据。
4. 验证忙碌状态事件与工程生命周期事件能否可靠作废任务。

**通过条件**：明确列出哪些操作能自动触发、哪些需要手动兜底；停顿数据足以定出上限。

### PoC-03：导出预设与映射正确性

测试普通 PBR、ORM、AoMetalRough（顺序不同）、8 / 16 位、多个 Texture Set，以及项目实际使用的 UDIM（若有）。

**通过条件**：预列的输出文件与实际导出一致；错误映射会阻止发布；不存在命名冲突或静默的通道错位。

### PoC-04：内存、显存、延迟与交互卡顿

| 维度 | 测试组合 |
| --- | --- |
| SP 工程 | 少图层 / 大量图层 |
| UE 场景 | 空白测试场景 / 正式角色 + 灯光场景 |
| 输出尺寸 | 1K / 2K / 4K |
| Texture Set | 单组 / 多组 |
| 同步模式 | 仅手动 / 空闲 3 秒 / 更短空闲时间 |
| UE 路线 | Auto Reimport；出现明显问题再测 PoC-06 的显式重导入 |

**至少记录**：

- UE 与 SP 同开时的基线可用内存、系统提交量、分页 / 硬错误情况。
- 同步触发时 RAM 与 VRAM（专用 + 共享）的峰值增量，以及插件常驻开销。
- SP 导出耗时、文件写入耗时、UE 重导入耗时、画面可见延迟（中位数与 P95）。
- 同步期间 SP 笔刷响应、UE 视口卡顿，以及连续多次更新后能否恢复。

**判定原则**：先测“UE 与 SP 同开但不启用同步”的基线。阈值在首次测量后确定，不预先编造固定的毫秒数或内存百分比。

### PoC-05：异常中断与一致性

覆盖：绘制中频繁修改；SP 导出中关闭程序；UE 关闭期间连续更新多批文件；UE 重启；磁盘空间不足；源路径移动；映射冲突；导出 Warning / Error；缓存目录被删除；目标文件被占用。

**通过条件**：旧版本不覆盖新版本，完整文件可以恢复，执行一次“完整同步”即可回到最新状态，不破坏 SP 工程或 UE 正式材质。

### PoC-06：UE 显式重导入对照（仅在路线 A 出现问题时进行）

1. 依据官方 API 独立实现最小的“指定既有 Texture 重导入”脚本，可参考附录 B 总结的思路，但不使用 SPsync 源码。
2. 用同一组 Texture、同一材质和相同的 2K / 4K 贴图，对比 Auto Reimport 与显式重导入的成功率、总延迟、峰值资源、资产标脏及配置保持。
3. 验证刷新后材质引用不变，并检查 sRGB、Compression、LOD Group、VT、Mip 等配置是否保留。

**通过条件**：给出“继续用路线 A”或“开发路线 B”的明确建议，附日志和可重复的测试步骤。

## 10. 最终验收场景

- **A. 正常绘制服装**：在 SP 中修改外套颜色、磨损或 Roughness，停笔后自动导出，UE 场景中原有材质显示更新；全程不手动导出或导入。
- **B. 高内存压力**：UE 与复杂 SP 工程同开，插件不会无限积压任务；卡顿严重时可暂停或切换手动，SP 仍能继续绘制。
- **C. 通道配置**：切换 ORM 与 AoMetalRough 预设时输出顺序明确；错误配置不会悄悄更新错误资产。
- **D. 正式材质保护**：既有 Master Material / Material Instance 结构与非目标参数不变，未授权资产不被覆盖，预览与正式发布按 D1 分离。
- **E. 异常恢复**：UE 关闭、文件发布失败或 SP 意外中断后重新启动，通过完整同步恢复到最新贴图。
- **F. 最终效果确认**：直接在 UE 原生视口判断材质，没有回传视频或多余的预览面板。

## 12. 风险与停止条件

| 风险 | 识别信号 | 应对策略 |
| --- | --- | --- |
| 同步影响绘制流畅度 | SP 笔刷卡顿、导出停顿超出上限 | 增大空闲间隔、减少输出、降预览分辨率；仍不达标则切换手动模式 |
| UE 重导入峰值过高 | RAM / VRAM 突增、明显分页、视口长时间停顿 | 先降低触发频率；再按同一测试矩阵评估路线 B，不能未经测量就改造整个插件 |
| UE 后台不刷新 | 切回 UE 才更新或延迟很大 | 配置指南给出后台设置；仍不可接受则作为路线 B 的依据 |
| 旧批次覆盖新批次 | UE 画面回退、清单版本倒退 | 每个目标单调版本号，发布前校验版本，队列只保留最新请求 |
| 部分贴图暂态错误 | BaseColor 已刷新而 ORM 尚未刷新 | 按 D4 结论处理；不可接受时使用 UE 显式批次处理 |
| 正式资产污染 | `.uasset` 频繁标脏、源贴图被预览版覆盖 | 按 D1 执行；检查源文件关联、源代码管理与正式发布流程 |
| 映射错误 | 不同 Texture Set 写同名文件、ORM 通道顺序不符 | 导出与发布前对路径、文件名、通道布局做硬校验 |
| 文件被占用 | 原子替换失败 | 有限次重试并上报，保留旧文件 |
| 插件升级造成兼容性断裂 | SP API、Qt 绑定或 Auto Reimport 行为变化 | 维护版本兼容矩阵与回归测试，明示首个支持的版本 |
| 许可证风险 | 拟移植 GPL-2.0-only 或未授权的商业代码 | 按 §2 约束只做独立实现 |

**正式进入开发的最低条件**：PoC 证明目标 UE / SP 版本能稳定更新同一个既有 Texture，32GB 机器上的资源峰值与交互体验可以接受，且 D1–D4 已定案。若不成立，开发任务先转为解决阻断问题，不扩大功能清单。

## 附录 B：参考项目研究结论

本附录只记录设计结论。按 §2 的许可证约束，两个参考项目的代码都不进入本项目。

### B.1 SPsync（GitHub 开源，GPL v2）

- 仓库：<https://github.com/yangskin/SPsync>。README 自述版本 0.971，支持 Painter 10.1+ 与 UE 5.4+；这是项目自述，不是我们的兼容性验证结果。
- 组件：SP 端单独即可完成 SP→UE 同步；UE→SP→UE 往返需要额外的 UE 侧 AssetCustoms，二者独立发布。
- **关键缺口**：它的“Auto Export”监听的是 `ExportTexturesEnded`，也就是 SP **完成一次导出之后**才通知 UE；我们需要的是纹理变化驱动的自动导出（FR-01），这部分必须自行实现。
- **值得借鉴的思路**（独立实现）：
  - UE 侧定向刷新既有 Texture：先确认目标资产存在，读取 `srgb`、`compression_settings`、`lod_group`，再以自动导入数据覆盖导入，导入后恢复这些设置。这说明“已有 Texture 定向重导入”不需要接管材质球。
  - 可配置的 UE↔SP 通道映射与往返 Profile。
  - 把路径、预设与 UI 配置存进 SP 工程 Metadata。
- **该思路的不足**（实现时必须补齐）：没有证明整批贴图都更新成功且属于期望的批次，不能当作原子事务或可靠回执；覆盖导入本身不是资产安全策略，仍需白名单、路径与身份核验、失败记录与版本控制；保留的属性不等于 Texture 的全部导入设置（还需检查源文件路径、VT、Mip、法线等）；显式导入同样消耗 CPU、RAM、VRAM 和 I/O。
- **不纳入**：AssetCustoms 双向资产管线、自动创建或修改材质与模型、高模烘焙、约 30fps 的持续视口同步。

### B.2 Xolotl Studio Live Link（商业插件）

- 官方商品页：<https://xolotlstudio.gumroad.com/l/fTRFN>。用户提供的 5.3.5 压缩包仅做过静态结构检查，没有运行；其中含非官方授权修改，不可信，也没有被授权复用。
- 官方页面并未把 UE 列为主要支持平台；压缩包中有 UE 安装目录，不代表目标 UE 版本获得官方支持。
- **可借鉴的设计思路**：
  1. 配置驱动的导出（通道布局、UDIM、格式、位深分开设置），而非写死文件名与通道。
  2. 导出前先列出拟输出文件，在占用资源之前发现冲突并建立可靠的文件映射。
  3. 控制消息与图像数据分离：若以后增加 UE 侧模块，只传文件路径和任务版本，不传像素数据。
  4. 其样例中的 AoMetalRough 布局（R=AO、G=Metallic、B=Roughness）与 ORM 不同，可作为通道校验的反例。
- **明确不采用**：以 Send / Update 按钮驱动的工作方式（不等于变化驱动）；UE 侧自动生成或重建材质、清除 Material Instance 参数覆盖的逻辑；每次导入后重编译材质的策略；通用跨 DCC 框架。

### B.3 结论对照

| 关键问题 | SPsync | Xolotl | 本项目选择 |
| --- | --- | --- | --- |
| 代码可否使用 | GPL-2.0-only，不能并入 GPL-3.0 仓库 | 无授权 | 两者都只借鉴思路，独立实现 |
| 既有 Texture 定向刷新 | 有实现思路 | 有导入覆盖逻辑 | 先测 Auto Reimport；必要时按 PoC-06 独立实现 |
| 绘制变化自动触发 | 无（导出结束后才触发） | 无（按钮触发） | 自行实现 FR-01 |
| 导出预设与通道 | 有 Profile 与往返映射 | JSON 配置直观 | 独立 JSON 配置（FR-02） |
| 对既有材质的影响 | 部分模式会创建材质 | 部分逻辑会重建材质或实例 | 强制只碰明确绑定的 Texture |
| 32GB 机器性能证据 | 无 | 无 | 必须在 PoC-04 实测 |
