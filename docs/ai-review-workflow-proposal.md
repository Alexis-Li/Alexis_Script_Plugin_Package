# AI 代码审核工作流优化建议

日期：2026-10-28。状态：供讨论的方案，尚未成为生效规则；对应工单
[#83](https://github.com/Alexis-Li/Alexis_Script_Plugin_Package/issues/83)。
本文件是方案的源文件，实施后的生效规则仍写入既有权威文档。

建议先在 MtoULiveLink 试行：功能开发前明确必要设计，按改动范围选择检查，
让独立审核和修复保护既有行为。必要验证通过且阻断项解决即结束，避免对假设中的
低价值边界反复测试。让设计与验证解决实际问题，减少重复工作和修复引入的返工，
让人工参与集中于需要判断和决定的事项。

本方案按你主导产品与发布、Agent 执行开发、本机承担主要宿主验证来设计，
不预设已有专职审核团队。现有提交、发布、权限及破坏性操作的授权边界继续适用。

## 依据与适用范围

核对了 Anthropic 于 2026-10-15 发布的
[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)。
最值得采用的是独立验证、按风险投入审核、限制无效复审，以及可恢复的交付。
文中的效率数据来自其内部实践，不能据此预测本仓库的收益。

本地依据是 `codex/mtou-preview-workflow` 分支的
`bbba40ce75918820eb681b0da104d02f2c07faf5`，不是对 `main` 或已发布版本的认证。
读取了规则、CI、测试入口、验收记录和近期提交；本次没有运行产品或宿主测试。
发布工单时已通过 `gh` 核实仓库访问、标签、相关 Issue 和分支基线；
远端分支保护、必需检查、当前 PR 评论与实际审核耗时尚未核实。StoUTextureSync 已注册为子模块，
本工作区没有其源码检出，未判断其内部 CI 是否充分。

## 建议的日常流程

1. **明确任务、设计与验证边界。** 沿用 Issue 的验收条件、排除项和决策；按下文规模
   明确职责、接口、必须保留的行为及最小验证。普通实现选择直接推进，产品取舍尽早由你决定。
2. **实现并自证。** 跑相关快速检查；涉及宿主行为时，准备真实用户操作、
   失败或退出路径的证据。重要 bug 的回归检查应能在旧实现或等价失败输入上失败。
3. **在可交付版本上做一次独立完整审核。** 在明确允许委派的任务或规则下，由未参与实现、
   使用新上下文的审查者读取需求、规则、完整 diff、受影响调用者及原始验证证据。
   不把实现者的推理记录作为正确性依据。无子 Agent 时使用独立审核会话。
4. **确认问题后修复并增量复验。** 先确认意见是否成立，再在正确的职责位置修根因；
   复验原问题及直接受影响的既有行为，保持原 finding ID。依赖、目标分支或实现范围
   改变且使原证据失效时，才扩大重审范围。
5. **集成前核对。** 发布针对最新 head 的审核，核对目标分支及组合结果、必要检查、
   阻断项和既有授权，再按现有流程集成并记录 SHA。
6. **按任务完成验收。** 区分实现、审核、集成、宿主通过和发布；满足约定条件后收尾。
   真实宿主缺失只阻塞依赖它的验收，不把未执行项写成通过。

PR 前独立审核可以直接成为 PR 上的正式审核证据：只要 base、head 和范围相同，
发布结论即可，无须因“PR 刚创建”再做同一次完整审核。之后每个新 head 仍需要
增量判断并更新已发布结论。默认一个独立审查者；有具体风险才增加安全或宿主专题审核。
新上下文有助于减少对实现思路的依赖，但不能替代测试和实际运行证据。
审查者先核实已有证据，只有证据不足、存在矛盾或需要验证新发现时才补跑检查。
一次审核通过就结束；两轮、三轮是观察或升级阈值，不是必须完成的次数。

## 功能开发前的设计与修复约束

现有 [领域规则](agents/domain.md) 要求读取适用的 CONTEXT 和 ADR，并指出与既有决策的冲突。
MtoU [整合方案](../composite/MtoULiveLink/docs/preview-workflow-integration-plan.md) 已包含共同接口、
状态归属、接管/恢复、分阶段实施及主风险短验证；
[ADR 0014](../composite/MtoULiveLink/docs/adr/0014-one-time-authority-and-staged-pose-groups.md)
记录时间控制权和姿势提交约束。通用开发流程应补上按改动规模使用这些设计依据的要求。

| 改动规模 | 开发前需要说明的内容 | 记录与决定 |
| --- | --- | --- |
| 局部修复或小功能，接口与状态归属不变 | 真实调用链、修复位置、直接受影响的行为和验证方式 | 在任务中简述后执行，不另写架构文档 |
| 跨模块功能，或改变公共接口、状态/资源归属 | 复用的能力、模块职责、数据/状态流、兼容约定、失败恢复及必须保留的行为 | 写入现有 Issue 或设计记录，实施前做一次针对关键设计的审查；普通技术选择自主处理 |
| 关键架构选择或真实宿主可行性未定 | 先确定决定后续方案的疑点，用最小原型或实验消除它 | 确认后再扩展实现；涉及产品取舍或改变既有承诺时由你决定 |

设计内容以能指导实现为限：谁拥有和修改状态，谁负责释放资源，调用者能依赖什么，
哪些现有行为不能改变，用什么最小证据判断成功。已有设计足够时直接引用，只有长期有效的
新决策才写 ADR；不为普通功能建立通用框架或要求多份候选架构。

防止“修 A 引入 B”的重点是把这些约束用于每次修复：

- 审核意见先经代码路径、契约或复现确认，不因“存在这种可能”就改实现。
- 修改前检查实际调用者和状态/资源所有者，在公共根因位置修正，避免让各调用者分别打补丁。
- 复验 A，同时检查修复直接触及的旧行为。已有测试能证明就复用；重要缺口补一个有判别力的回归检查。
- 不通过删除已有断言、放宽阈值、吞掉错误或改写验收标准把 B 变成通过。若原判定确实错误，先给出独立依据。
- 修复若要求改接口或状态归属，先回到设计判断。连续补丁正在扩大影响时，停止叠补丁，
  检查并撤回本任务不成立的修法；保留用户改动和仍有效的修复。

例如关闭一个参考窗口时，先确定窗口资源与联动会话分别由谁拥有，明确关闭窗口是否应保留
最近结果和活动会话。随后验证关闭/重开及这两个相关行为，就能同时约束原问题与直接回归风险。
架构设计能减少这类错误，但不能替代对误报、测试判定错误和局部修复影响的核实。

## 风险决定检查深度

按行为、影响范围和恢复成本分类，不能只看文件扩展名或改动行数。

| 等级 | 本仓库中的例子 | 建议检查与人的参与 |
| --- | --- | --- |
| 低 | 不改变契约的错字、链接、排版修正 | 沿用现有小文档修改路径，核对事实与适用检查；已有授权下直接完成 |
| 常规 | 单组件局部功能、可撤销操作、普通 UI 行为 | 快速测试、一次独立审核、受影响宿主路径；你只处理未决产品问题和确需判断的效果 |
| 高 | 可能误删或覆盖资产、破坏兼容/状态恢复的协议改动、改变线程或回调资源所有权、放宽发布权限或掩盖关键失败的判定修改 | 针对具体危险路径复核，验证必要的失败恢复及兼容性；你审重要取舍和恢复证据；已有第二位专业负责人时再增加对应人审 |

规则、测试或文档如果改变删除指令、安装步骤、兼容承诺或放行标准，也可能属于高风险。
同一 PR 有多个风险时按最高必要等级处理。提高等级须指出真实触发路径、影响或未满足的
契约；仅碰到某个目录、回调函数或测试文件不构成升级依据。

## 验证的选择与停止条件

开始工作时简要确定“需要证明的行为、最小有效检查、何时结束”；小任务一句说明即可，
不增加专用报告。选择依据是实际触发可能、后果、改动关联性和新增证据的价值，
不把所有能想象到的边界组合都变成验收条件。

- 保留适用的项目必需检查。新增或扩大检查须对应未覆盖的验收项、已有失败，
  或由代码/宿主证据支持的具体回归风险。
- 优先现有测试及代表性输入。同一行为已有充分证据时，额外测试方法、重复运行或第二位审查者
  应说明能发现什么尚未覆盖的问题。确有不同失败机制时才采用互补检查。
- 对超出支持范围、无真实触发链、需要多个无依据假设同时成立的情形，不默认新增测试或防御代码。
  不为其增加重试、兼容层、配置和降级分支。
- 低概率但可能误删资产、破坏工程的可达路径，保留针对性验证；不因此枚举无关组合。
- 修复后只复测受影响部分；所需检查通过、验收覆盖且没有阻断项后即结束。
  不因“再保险一次”重跑全部套件，也不让审查者重复执行已核实的相同检查。
- 耗时检查在有必要时说明它证明什么以及为何现有证据不足，然后在已有授权内执行。
  不设“测试必须短于编码”的硬比例，也不用时间额度耗尽作为跳过必要检查的理由。

这里的停止条件同样约束架构讨论：已明确职责、契约和验收且没有影响方案的疑点时即可实施。
不把节省下来的测试时间转成没有决策价值的长时间设计。

风险等级只决定检查深度，不授予合并、发布或删除权限。已有授权不重复询问；
出现未覆盖的操作或重要新取舍时，提供可审查结果后再请求决定。

GitHub 不允许 PR 作者批准自己的 PR。沿用现有“在同一账户下发布审核评论”的做法时，
应明确它是审查记录，不能当作另一位人的 approval。若当前主要由一个人负责，
先采用可执行的核对与责任机制，不把“两个人审”写成无法满足的固定门槛。
参见 [GitHub 审核规则](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)。

## 让审核有用并及时结束

沿用现有“已确认缺陷、待验证风险、验收缺口、后续候选”和稳定 finding ID，
补充以下操作约定，不另建一套分类文件：

- 每个问题说明触发条件、实际影响、代码位置或证据、完成条件；严重程度和是否阻断分别判断。
- 需求违背、兼容性破坏、数据损坏及关键验收缺口优先。风格问题交给已有确定性检查；
  没有项目规则依据的个人偏好不触发返工。
- 同类缺陷一次说明并检查受影响位置，避免每轮只报一个实例。
- 原有问题标明来源；与本次改动及安全运行无关的改进记为候选。既有缺陷若被新路径触发，仍需处理。
- 每条已发布意见给出明确处置：修复并复验、证据证明不成立、符合已同意设计，或经授权延期。
  “作者觉得没必要”不自动等于误报，也不能用于绕过阻断项。
- 第一轮完整审核，后续审核增量及依赖。修改未涉及、证据仍有效的部分复用结论。
- 到第三轮仍反复出现同类问题时，停止自动来回打补丁，转为根因诊断、缩小改动或重新设计；
  已确认阻断项继续阻断，轮次上限不是放行条件，也不是放弃任务的理由。

需要问你的问题应汇总为真正的产品取舍、无法消除的风险或授权缺口。
普通修复和复测由 Agent 连续完成，不把每轮审核变成一次人工确认。

## 自动检查与宿主验证

CI 按项目和真实依赖选择检查。当前 workflow 在所有 push/PR 上运行根测试，根测试包含
MtoU 协议、打包和构建脚本检查，因此当前修改其他插件也会触发这些检查。
目标是将产品专用检查与共享工具检查分开，避免只加一个所有 PR 都运行的 MtoU job。

| 本次改动 | 应触发的检查 | MtoU 产品测试 |
| --- | --- | --- |
| 只修改其他插件的独立实现 | 该插件相关检查 | 不运行 |
| 修改 MtoU 实现、协议或测试 | MtoU 相关快速检查及按需宿主验证 | 按受影响范围运行 |
| 修改被 MtoU 使用的公共打包工具 | 工具测试和相关包契约检查 | 只追加受该依赖影响的检查，不自动编译 UE 或启动 Maya |
| 修改集合注册、子模块 pin 或布局 | 集合注册、布局及必要的固定提交验证 | 不运行无关联的 MtoU 产品套件 |
| 只修改使用说明、错字或链接 | 适用的文档/链接检查 | 不运行；规则或兼容承诺变动另按实际影响判断 |
| 修改影响检查选择或执行方式的 CI 配置 | 验证选择逻辑和受影响 job | 依实际覆盖范围确定 |

子仓库开发由其自己的 CI 负责；集合仓库更新 pin 时核对注册和子仓库交付证据。
产品专用的协议检查迁入产品测试入口，共享打包工具自身的测试仍归根 tests；
根测试按共享工具、模板、规则和结构等实际变动触发。选测规则覆盖新增、删除及重命名，
并保留必需检查的明确完成结果，不用无结果的跳过掩盖应运行而未运行的测试。
只有成功完成改动及依赖判定，才能标记“不适用”。比较基线不可用、选择器异常，
或相关路径/依赖尚未纳入映射时，明确失败并修正判定；若采用回退检查，须预先限定
其范围并说明能覆盖的风险，不能将选择失败按空集合成功，也不自动启动所有宿主测试。

MtoU 的纯 Python 产品测试使用已有命令：

```powershell
python -m unittest discover -s composite/MtoULiveLink/maya/MtoULiveLink/tests -p "test_*.py"
```

迁移保留现有协议语料检查的覆盖，按失败定位需要单独运行。
先验证这些测试在 CI 环境可重复运行，再确定必要的平台矩阵。
系统 Python 测试不代表 Maya 内置 Python、Qt 或 UE 兼容性已经通过。

| 改动类型 | 应复用的验证入口或证据 |
| --- | --- |
| 仓库工具、模板、布局、共享流程 | 现有 `validate_repository.py` 与根 `tests/` 门禁 |
| Maya API、Python 兼容性 | 产品纯 Python 测试、Maya 2024 `mayapy`；按产品规则补 Maya 2022.4 |
| 窗口、回调、关闭/重开 | `maya_gui_window_check.py`，覆盖两种退出方式与 Script Editor 异常 |
| 安装、打包或升级 | 实际打包产物、`maya_gui_install_check.py`、安装/升级/失败恢复及回退 |
| UE C++ 或运行行为 | 支持引擎编译、相关 Automation 测试；真实画面使用可渲染运行方式 |
| 协议、控制权、跨宿主状态 | 两端测试及受影响的真实 Maya–UE 联合场景 |
| 视觉或性能 | 固定样本、实际引擎/宿主构建和环境；视觉按既有 BaseColor 要求；性能保持同一首选项哈希 |

正式检查选择以 [MtoU 规则](../composite/MtoULiveLink/AGENTS.md) 为准。
普通迭代只跑受影响检查；改动稳定后完成确实适用的项目必需套件。
宿主检查按最终受测版本和具体失效条件重跑，不因又收到一条评论就全部重跑。

短期继续用本机已有宿主和测试脚本，先验证可重复性。只有无人值守运行确实稳定后，
再考虑专用 runner。真实 GUI、端口、首选项、GPU 和宿主安装可能共享；
不同 worktree 不代表这些资源隔离，同一宿主环境的验收应串行执行。
使用可丢弃场景副本和隔离首选项，不接管正在工作的生产会话。

### 每次交付的最少证据

把下面内容放进现有 PR 的 Validation 部分，详细数据链接到测试产物，避免重复报告：

- **版本对应：** base/head、实际测试 checkout SHA、包或二进制标识；如果 CI 测的是临时合并提交，
  明确其与目标分支和 PR head 的对应。宿主还要确认实际加载的代码，不只记录工作区版本。
- **执行信息：** 命令、宿主构建、必要样本/配置标识、退出码、实际运行项、失败/跳过项及证据位置。
- **验收结果：** 对应验收条件、观察值与判定依据、失败/退出路径、未覆盖内容。

测试汇总至少区分通过、失败、跳过、前提缺失和不适用。可选测试缺参数、实际运行数量为零、
缺结果文件、加载旧插件时，不能据外层返回码给出“宿主通过”。
优先在现有测试报告生成处补这些判定，无须先建设通用调度平台。

“测试通过”的正确性也应纳入审核。新增关键回归检查时，至少确认它能识别所修复的失败，
而非仅验证测试自身创建的理想状态。界面仍显示、进程退出成功和源数据正确，各自只证明一部分。

日常摘要留在 PR；宿主原始产物按需要保留；只有不可替代的测量、校准和设计结论进入
现有 project-history。继续复用 `issue_report.py` 做状态评论结构检查，
但结构合格不能当作证据真实或验收完成。

## 集成与本地插件发布

**先做好串行集成。** 合并前检查最新目标分支，把 PR 应用到该目标上的结果纳入验证，
对目标漂移和冲突解决单独判断；继续使用现有 `--match-head-commit` 保护。
这个参数只保护 PR head，不替代目标分支检查或服务端保护。
若需要多人并发集成的严格保证，再配置服务端最新基线检查或合并队列。

GitHub 原生合并队列有仓库归属和套餐限制，不能假定本仓库可直接启用；
启用后 CI 还需处理 `merge_group`。
参见 [GitHub 合并队列文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)。
实施前核实远端设置，不把本地流程当作已经存在的服务端强制门禁。

**发布采用受控试用和恢复验证。** 使用内部测试场景，再交付明确标注的候选安装包，
覆盖约定的升级、旧工程、退出和失败恢复场景后发布正式包。晋级依据是用例完成，
不机械规定等待一周。MtoU 产品版本仍只在发布任务调整；开发测试包用提交与哈希辨识。
跨宿主包标明互相兼容的组合，保留上一组可用产物和可执行的恢复步骤。

新功能确有隔离需求时，可设计默认关闭的本地实验开关，验证后及时收敛。
本地插件不应依赖远程开关作为主要恢复手段：替换代码无法恢复已经覆盖的文件、
破坏的场景或不兼容的数据。涉及这些行为时，应在交付前证明撤销、恢复或备份方案有效。

普通开发 pin 更新采用子仓库已审核、已验证并推送到远端的提交；无需为每次 pin 更新正式发版。
父仓库核对固定提交、审核和验证证据、兼容性与可获取性；不对相同子仓库 diff 重复完整审核。
正式发行时，另按拥有该产品的仓库规则核对发行版本、安装产物及发布验收证据。
沿用 [发布流程](release-process.md) 与 [子模块边界](submodules.md)。

## 最小落地顺序与效果判断

| 顺序 | 具体改动 | 完成标准 |
| --- | --- | --- |
| 第一批 | 在现有流程补按规模进行的开发前设计、验证停止条件及修复影响检查；PR 模板增加必要的风险和恢复说明；CI 按项目分流并接入 MtoU 产品 Python 检查 | 一个真实代码 PR 能跑通；无关联的插件改动不触发 MtoU 产品检查；混合项目、共享依赖和选择器失败的用例验证通过；已有证据足够时及时结束，无须增加重复报告 |
| 第二批 | 在现有宿主报告中补齐版本对应和缺前提判定；按产品规则整理改动到测试的选择；演练候选包升级与恢复 | 零执行、旧代码、缺参数均不能被记为验收通过；候选包能安装并恢复 |
| 第三批 | 从已确认缺陷和干净改动建立小型审核样本；依据实际效果调整审查深度 | 能判断审核是否发现真实问题、减少误报和重复工作，以及修复是否保护既有行为 |

首批主要修改位置是 `.github/pull_request_template.md`、`.github/workflows/validate.yml`、
`docs/agents/issue-tracker.md`、`docs/development-conventions.md`，以及迁移产品专用检查涉及的测试入口；
产品验证细节继续归 `composite/MtoULiveLink/AGENTS.md` 和已有测试。
根 AGENTS 继续链接权威流程，不复制正文；暂不额外增加 REVIEW.md、专用审核平台或全仓每夜扫描。
采纳后将确定内容写入对应权威文件，并处理本提案的归档或删除，避免出现两份生效规则。

试点选择 MtoULiveLink 的常规修改和高风险安装/生命周期修改中的若干真实任务，
利用现有 Issue、PR 和运行证据观察效果，按任务范围和风险理解差异。

效果判断关注以下问题：

- 开发前的设计是否澄清实际职责、契约和关键疑点，并减少实现后的反复推翻。
- 检查是否覆盖必要行为；是否存在无依据的边界枚举、同一结论的重复验证，或证据足够后继续探索。
- 审核是否发现真实缺陷；修复是否保护既有行为；误报、重复意见和无关改进是否造成返工。
- 人工是否在产品取舍、效果判断、重要风险和必要授权时介入，普通实现与复测是否自主完成。
- 验收证据是否真实且与受测版本一致；出现漏检时，能否找到具体失效环节并针对性改进。

耗时、等待和审核轮次仅在有助于定位重复工作或流程阻塞时作为辅助信息，优先取自已有记录。
是否值得投入，取决于它能否澄清必要决策、验证实际风险或形成有效证据；必要设计、宿主验证
和人的审慎判断可以合理增加耗时。流程成效依据工作价值、验证充分性和返工情况综合判断，
不设固定提速比例，也不以耗时增加单独判定失败。

审核样本先从上面的真实记录选取，经核实后保存引入问题的 base/head、最小触发场景、
确认缺陷和修复引用，再加入少量经人工确认的干净改动。运行评估时不给审查者修复答案，
保留未用于调提示的样本。每次调整审核方式再重跑，不要求每天消耗一次完整评估。

预期的用户体验是：小改动采用相称的设计和检查，功能改动先说明关键设计，开发其他插件不会等待
无关的 MtoU 套件，审核意见经确认后才驱动修复。需要你参与的是实际取舍、效果判断和未覆盖的
授权；已授权的开发、复测和收尾连续完成。汇报给出结果、关键证据和剩余问题，不要求你阅读长日志。

本轮交付仅为方案。自动合并、远端规则变更、新付费服务、发布以及子仓库变更，
均不因这份提案而获得授权。
